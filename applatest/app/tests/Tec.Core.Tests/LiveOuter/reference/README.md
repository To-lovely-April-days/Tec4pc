# LiveOuter 的 Python 参考实现和对拍数据怎么来的

`src/Tec.Drivers.Rd105/TecControl/Control/LiveOuter.cs`（串级外环「按实测实时算」）是照这里的 `outer_m.py` 逐行移植的。
试算成绩（改动方案 F 节）是 Python 版跑出来的，所以 C# 版必须跟它「同样的读数进去，出同样的数」——
上一层目录的测试就是在核这件事。这个目录留着参考实现和生成脚本，为的是以后参考实现改了能把对拍数据重生成出来。

这里的 `.py` 不参加编译，也不在测试里执行（测试只读 `../golden/` 下的数据，和 `outer_m.py` 里 `PARAMS` 那一段文字）。

## 文件

| 文件 | 是什么 |
|---|---|
| `outer_m.py` | 参考实现，定稿原样拷贝（类 `M`，缺省参数 `PARAMS`）。md5 `46e5ed1f62d32808ec864d72674ad067`（LF 行尾）。**不要在这里改它**：`gen_synth_golden.py` 的插桩是按行号挂的，md5 对不上就拒绝运行 |
| `outer_api.py` | `outer_m.py` 要的最小定义：`Obs`（一拍的输入）和 `OuterLoop`（基类）。从试算台的 `bench/outer_api.py` 里只留了这两样 |
| `gen_synth_golden.py` | 合成对拍场的生成脚本 → `../golden/synth/s01…s12_*.csv`。自己造输入（确定性，没有随机数），带插桩和每场的「必须走到的分支」断言。s12 另含 `LiveOuter.PinTarget` 的 Python 等价写法（见下） |
| `gen_whitebox_steps.py` | 白盒向量的生成脚本 → `../golden/whitebox/whitebox-steps.json`。逐拍对拍走不到的分支：把内部状态摆好走一整拍 |
| `regen_real_golden.py` | 真机对拍夹具 `../golden/real/*.csv.gz` 的核对 / 重生成（只用夹具里自带的输入，不靠仓库外的东西） |
| `golden.py` | 真机夹具当初的生成脚本，原件备查（md5 `52c0e8036a761cd36cd0397b15dbc488`）。它要读仓库外的现场逐拍记录和 `evidence/core.py`，换台机器跑不了；要核对 / 重生成用 `regen_real_golden.py` |

只依赖 Python 3 标准库（生成时用的是 3.9.6）。跑的时候带 `-B`，免得在仓库里留下 `__pycache__`。

## 对拍数据

### 真机 6 场（`../golden/real/*.csv.gz`，9607 拍，gzip 后 591 KB）

Python 定稿在现场逐拍记录上**开环重放**：记录里的夹套是现在的程序走出来的，这里只核「同样的读数进去算出来是不是同一个数」。
全量是 14 场 20898 拍（3.3 MB）；进仓库的是其中 6 场，原样 gzip（`gzip -n -9`，解压后跟原件 md5 相同）：

| 20261109-095506 | 1869 | 19.3 → 50 ℃：出厂三个数就是照它拟的；有等人答复开冷却水 | `95929992c2b7c310fba73a5be3402e3c` |

表头 `t_s,dt_s,sp,tr,tj,wall,xr,b,tau,tau_ekf,k,p_up,g_sp,to_eff,u`：前 5 列是输入，后 10 列是这一拍 `step` 返回之后的内部量
（Ŵ、T̂、b̂、τ̂、第二路的 τ、K、P上限、g_sp、To′、没夹过的夹套目标）。喂法（照 `golden.py`）：
第 0 行先 `reset` 再 `step`（`first = True`），`dt` 用 `dt_s` 列；热源在加热棒侧（`side = 'H'`）、输出开着、不贴下限、不挂起；不给终点和坡速。
所以真机场里**报警永远不响、斜坡段永远不进、终点永远不变、每拍都有读数**——这些分支只靠合成场。

为什么是 gzip：6 场原文 1.54 MB，加上合成场就超过给夹具定的 1.5 MB；gzip 后 0.59 MB。测试用 `GZipStream` 直接读。
（2026-11-14 加了 s12 之后夹具合计 1.24 MB；生成脚本里合成场的大小上限从 600 KB 放到 660 KB。）

### 合成 12 场（`../golden/synth/*.csv`，3249 拍，613 KB）

表头多出输入 7 列和报警 2 列：
`t_s,dt_s,sp,sp_final,sp_rate,tr,tj,side,inner_sat_low,tec_withheld,output_on,first,` + 上面那 10 列 + `alarm,alarm_on`；s12 在行尾再多一列 `pin`。

- `first = 1` 的行：先 `Reset` 再 `Step(first: true)`；其余行只 `Step`。**s05 有两行 `first = 1`**（第 0 行和第 310 行）。
- `pin = 1` 的行（只有 s12 有这一列）：这一拍喂的目标是占位的（不在控，目标 = 当时的读数），`Step` 之前先 `PinTarget(sp)`（`first = 1` 的行是 `Reset` → `PinTarget` → `Step`）。
  **Python 定稿没有这个入口**，`outer_m.py` 一行没改；生成脚本里是它的等价写法——`step` 之前摆四样：
  `est.ref = obs.sp`；`est.spf_prev` 不是 `None` 的话 `est.spf_prev = obs.sp`；`est.g_sp = 0.0`；`P[0][2] = P[2][0] = P[1][2] = P[2][1] = 0.0`。
  脚本对每一个 `pin = 1` 的拍断言：门控正好是 0，τ̂、第二路的 θ、P₂₂ 逐位不动。
- `tr` 空 = 这一拍没读数（喂 NaN）；`sp_final` / `sp_rate` 空 = 没给；`side` 是 `H` / `C`。
- `u` 是没夹过的（s08 里有 72 拍在 −50…200 之外）。`alarm` = 这一拍报出来；`alarm_on` = 条件成立着。
- 喂进 Python 的每个输入都先按打印精度取整，所以从 csv 读回来的输入跟 Python 喂的逐位一样。

| 场 | 走的是什么 |
|---|---|
| s01_step_plain | 没在控（目标 = 读数）→ 30 → 72 ℃（比例贴着 P上限）→ 目标改到读数下面（降温方向不封顶那一支） |
| s02_ramp | 升坡、降坡（终点、坡速），「坡那一行」和「直接去终点」谁说了算各走到；几种边角给法 |
| s03_retarget | 目标中途改：大改、小改、极小改，对 τ 的把握按 Δ² ÷ (Δ² + 25) 放开 |
| s04_tau_hi | 真 τ = 5200 s：第二路顶到 3 倍、回归值夹在上限，τ̂ 到 2783.7 |
| s05_tau_lo_reseed | 真 τ = 150 s：第二路贴到 0.4 倍、K 贴 1，τ̂ 到 384.3；用过的对象第二次 Reset；连续 120 s 没读数 |
| s06_glitch | 单个坏点 ±5 K（进不来）、连坏两个（第二个进来） |
| s07_loss | 升温途中没读数：起算后第一拍、单拍、3 拍、30 s；None 和 NaN 两种 |
| s08_far | 读数离模型远：To′ 夹到 20 s；夹套目标远远冲出 −50…200 |
| s09_alarm_combo | 报警条件组合：报 8 次；四个开关量各缺一个不报；顶满差一拍不报；不升了撤、再升再报；釜壁比釜内热不报 |
| s10_exo_dt | 放热 + 拍长 0.5…3 s 混着；顶满计时按不齐的 dt 累加；报警报在没读数的拍上 |

| s12_idle_pin | 占位目标（`pin` 列，118 拍）：没在控（含起算那一拍）→ 下发 40 → 55（真 τ = 700，两路都认动）→ 过渡没完就停控：夹套自然凉、釜内自己走，其间单个坏点、连坏两个、两拍没读数（占位目标沿用上一个）、加冷料掉 15 K → 再下发目标（把握照「新目标 − 上一拍读数」放开）。喂法跟挂接层一样，不给终点和坡速 |

这些场的对象是随手造的（夹套 120 ℃ / −10 ℃、读数一下掉 25 K、真 τ = 150 / 5200 s），只为把分支走到——
里面的 u、b̂、τ̂ **不能拿来说新算法好不好**。而且合成场的期望值就是 Python 版自己的输出：它证明「C# 跟 Python 一样」，不证明 Python 版本身对。

### 白盒向量（`../golden/whitebox/whitebox-steps.json`，17 个）

定稿参数下任何喂得出来的输入都走不到、逐拍对拍核不到的分支：第二路相关系数夹 ±0.999（8 个）、P₂₂ 贴下限 1e-18、
θ 正好在边上也清相关（2 个）、回归权重和 ≤ 1e-9 提前返回、ρ = 0 时升温方向不给比例（3 个：e > 0、e ≤ 0 的对照、K 贴 1 时不出 NaN）、
中值缓冲里两个不一样的数取大的（2 个）。
每个向量 = 标准第一拍之后把内部状态摆成「调用前」、走一整拍、记「调用后」；数是 17 位有效数字的全精度字符串，键名 = C# `LiveOuterState` 的属性名。
C# 那边用 `ImportState` / `ExportState` 摆和取。

## 容差

- csv 里印 9 位小数的 7 列（wall、xr、b、k、p_up、g_sp、u）：绝对差 ≤ 1e-9；印 6 位小数的 3 列（tau、tau_ekf、to_eff）：≤ 1e-6；`alarm` / `alarm_on` 必须相等。
- 白盒向量是全精度的：相对差 ≤ 1e-12。
- 依据：打印取整本身就有半个末位（5e-10 / 5e-7），容差是它的 2 倍。C# 跟 Python 真正的计算差别只有两处——
  平方（Python 的 `x ** 2` 走数学库 `pow`，C# 写 `x * x`，偶尔差 1 ulp）和数学库 `exp` / `tanh` 的末位。
  2026-11-14 在 macOS arm64（.NET 8.0、Python 3.9.6）上把 C# 的全部内部量按全精度倒出来比过：
  进仓库的 17 场 12556 拍里 12547 拍全部内部量逐位相等，其余最大差 1.4e-14；全量真机 14 场 20898 拍最大差 2.3e-13（第二路的 τ）。
  Windows 上数学库不一样（没实测），按在 Python 里把 `exp` / `tanh` 随机拨 ±1 ulp 的试验，漂移在 1e-12 以内。
- **对不上先当移植抄错查，不许放宽容差**：抄错一处通常差 1e-6 以上。也不要比格式化后的字符串（末位悬在 5 上的拍会因为 1 ulp 翻一位）。

对不上时怎么找：`python3 -B gen_synth_golden.py --out /tmp/x --debug-dir /tmp/x/wide` 出一份加宽的逐拍内部量
（`%.17g`，含第二路的 T₂ / b₂ / θ / P、回归的 6 个累加量、中值缓冲等），拿 C# 的 `ExportState()` 逐拍比，找第一处分叉。

## 什么时候要重生成、怎么做

参考实现（`outer_m.py`）变了——算法改了、`PARAMS` 改了——三样数据都要重做，C# 也要跟着改到重新对上：

1. 换掉 `outer_m.py`；把 `gen_synth_golden.py` 里的 `OUTER_M_MD5` 改成新的，**并核一遍插桩挂的行号**（类 `Tracer` 里的 `ln == …`，
   行号变了插桩会挂错地方；脚本里每场的必达清单断言会帮着发现）。
2. `python3 -B gen_synth_golden.py`：重写 `../golden/synth/`，打印覆盖表，全部断言过了才返回 0。
   `python3 -B gen_synth_golden.py --no-trace`：不挂插桩再跑一遍，核 csv 逐字节一样。
3. `python3 -B gen_whitebox_steps.py`：重写白盒向量（每个都用插桩确认走到了点名的那一支）。
4. `python3 -B regen_real_golden.py --rewrite`：用夹具里的输入重放，把内部量那 10 列重写（输入 5 列不动）。
   不加 `--rewrite` 是只核对：现在这份夹具跟参考实现对不对得上（应当输出「都在容差内」）。
5. 改 `LiveOuter.cs`，跑 `dotnet test tests/Tec.Core.Tests --filter "FullyQualifiedName~LiveOuter"` 到全绿。
   场数 / 拍数 / 报警次数变了的话，`LiveOuterFixtures.cs` 和 `LiveOuterGoldenTests.cs` 里钉的数跟着改。

参考实现没变、只想确认数据没被动过：第 2 步的 `--no-trace`（合成场逐字节）和第 4 步不带 `--rewrite`（真机场在容差内、md5 对得上表里的）。

要换一批真机场：全量 14 场在设计材料的 `plan/out/golden/` 下（仓库外）；`gzip -n -9 -c 原件.csv > ../golden/real/场名.csv.gz`，
再把 `LiveOuterFixtures.Real` 和 `LiveOuterGoldenTests` 里的名单、拍数改掉。

## 移植时最容易错的地方（改 `LiveOuter.cs` 之前先看）

1. 第一拍 = 同一个输入先 reset 再 step。观测器（釜壁估计、两路认 τ、T̂ / b̂）整段不跑，但过渡参考、控制律、顶满计时、报警照跑。
   reset 预放了一个读数、step 又推一次，所以起算后来的第一个新读数进不来（`median(tr0, tr0, tr1) = tr0`）。
2. 一拍里的次序：釜壁估计 → 第二路（用上一拍的门控、这一拍的 Ŵ 和它的变化率；没读数也推）→ 第一路（有读数才跑；下限用这一拍刚算的 τ₂）
   → 估计器（τ̂ 用改过之后的，ε 用旧 T̂，T̂ 和 b̂ 都从旧值各走一步）→ 「终点变了」→ 过渡参考 / 门控（给下一拍用）→ 控制律 → 报警。
3. 没读数的拍：不进中值缓冲也不清；第二路只推不修；第一路整个不跑（滤波量、累加量都不动）；ε = 0 但它的 20 s 平均照样往 0 回；公式照出；报警照算照报。
4. reset 不清 τ̂、K、ε 平均、门控、顶满计时、报警状态、上一拍终点；第二路从此刻的 τ̂ 重新起（θ = 1/τ̂ 不是 1/τ̂₀）、把握回先验；回归累加量清零。
5. τ̂ 变了（Δ ≠ 0 才动）：先用旧 τ̂ 算斜率换算 b̂，再换 τ̂、重算 K。上限 3·τ̂₀ 夹的是回归值，τ̂ 本身不夹。
   回归值的下限 = max(0.4·τ̂₀, min(τ̂₀, τ₂))。第二路 θ 用 ≤ / ≥ 判顶边，顶边时 P₀₂、P₁₂ 清零。
6. Python 内置 `max` / `min` 是「第二个更大 / 更小才换」，遇 NaN 跟 `Math.Max` / `Math.Min` 不一样；`x ** 2` 走 `pow`，C# 一律写 `x * x`。
7. 夹套目标在公式里不夹（−50…200 是出口另给的）。e ≤ 0 走线性不封顶，e > 0 走 P上限·tanh。
   斜坡段进的条件是「坡速 ≠ 0 或 终点 ≠ 目标」；取 min 还是 max 看的是「终点 ≥ 目标」，不是坡速的符号。
8. 报警：60 s 窗先追加再弹，弹的条件是严格 <；顶满计时按 dt 累加，四个开关量有一个不成立就当拍清零，判 ≥ 60；
   条件每拍照抄，从假变真那一拍报，没有冷却时间。
9. 「终点变了」比的是终点（没给就用目标），不是目标。坡速没给 / 0 都当 0（别拿 NaN 当「没给」）。
10. 两个数的中值取大的。第二路的 P 对称化只在有读数的修正之后做。
11. `Reseat`、`PinTarget` 是 C# 多出来的入口，都只在 `Step` 之前摆状态、`Step` 一行不改。次序：`Reset` / `Reseat` → `PinTarget`（这一拍的目标是占位的才调）→ `Step`。
    `Reseat` 不动上一拍的终点（在控时断档里目标真改了，紧跟的 `Step` 照常放开把握）；`PinTarget` 摆过渡参考、上一拍的终点（有才摆）、门控、P₀₂ / P₁₂ 四样，别的（P₂₂、θ、P₀₁……）不许碰。

## 对拍钉不住的（照搬的，改的时候自己小心）

- 第二路 P₀₀ / P₁₁ 的下限 1e-12：每拍都往上加噪声，连摆状态都到不了。
- reset 不清顶满计时 / 报警状态：没有「报警响着的时候再 reset」的场（产品里一个对象只 Reset 一次，那时两样本来就是 0）。
  （reset 不清上一拍的终点：s05 的第二次 reset 目标没变，对拍钉不住；由性质测试「Reset不清上一拍的终点…」钉着。）
- `LiveOuter.Reseat`（断档后重摆）Python 里没有对应的入口，做法照试算台「两炉之间带着 τ̂」的包装（Reset 再把 θ、τ₂、P₂₂ 放回去），
  另清顶满计时和 ε 的平均；它只有性质测试和挂接层测试，没有对拍。试算台那个包装（`checks.py` 的 `Carry`）还有一句 `o.spf_prev = obs.tr`
  ——那是「两炉之间不在控」的喂法，C# 里归 `PinTarget` 管，`Reseat` 自己不动上一拍的终点。
- `LiveOuter.PinTarget`（不在控时目标只是占位的）Python 里也没有对应的入口；它有对拍（s12，按上面的等价写法生成）、性质测试和挂接层测试。
  试算台里「开控前估计器早就在跑」那几行（`attack-robust/xsim.py` 的 preroll：`obs.sp = 釜内读数`，没有这四样）是**不带 Pin** 的喂法跑的，
  成绩不能直接算在带 Pin 的产品喂法头上。
- 输入不合法（dt ≤ 0、夹套读数无效）：Python 是抛除零 / 让 NaN 进状态，C# 是先抛、不动状态——有意不一样。
